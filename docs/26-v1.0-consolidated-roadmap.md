## 0. How to use this

Work the stages **top to bottom**. Each stage lists: its goal, the exact open items it closes (with
the source doc), dependencies, the sub-steps, and a Definition of Done. Every sub-step is meant to be
**independently committable and CI-green across the tri-runtime** (Worker/D1 · Node/SQLite · Bun), per
the project's existing bar. Nothing here re-opens a decision already ACCEPTED in `docs/14`.

## 3. The ordered plan

**Ordering rationale.** (1) Finish cheap loose ends first (derisk, complete the map story). (2) Build
the **packet stack (P1–P4)** — the largest remaining capability and the foundation the retro shell
needs. (3) Apply the **Cogmind theme** only once the component set is stable (a theme re-skins finished
surfaces; theming churning ones wastes effort). (4) Do the **retro-shell transformation (P5)** on top
of the theme + packet surfaces. (5) **Release prep last**, so screenshots/marketing reflect the final,
themed product. CI is explicitly post-1.0.

### Stage 0 — Loose ends (small, fast, completes the map story)
*Closes O1. No dependencies. ~a few slices.*
- **0.1 Telemetry & weather graphs** — add `uPlot` (tiny, dependency-light) charts to the station
  detail (workbench): temperature/humidity/pressure/wind from `sensor_readings`, and speed/altitude/
  course over the position track. Reuse the existing `getStationTrack` + a new `sensor_readings`
  windowed read. Honors reduced-motion; lazy-loaded so the cacher surface stays light (`css.md`).
- **0.2 Raw per-station packet view (workbench)** — a live + recent raw TNC2 frame log per station, in
  the workbench only (kept off the cacher surface per ui-ux). Back it with a hard-TTL `packets_recent`
  store (cost rule); the browser RF panel already renders live frames — add the per-station history.
- **0.3 "Navigate to cache"** — a one-tap field action on the cache sheet: bearing/compass readout
  (we already compute the great-circle bearing) + hand-off links to device maps / OSRM directions.
- **DoD:** charts render in both density modes; raw view TTL-bounded; navigate hand-off works on
  mobile; tri-runtime green.

### Stage 1 — Packet radio P1–P4 (the long pole)
*Closes most of O2. Depends on `packages/ax25` (P0, done). Each phase ships independently + CI-green.
Detail lives in `docs/25` §8.*
- **P1 — Browser packet terminal** ("Graphic Packet reborn"): multi-channel connected-mode terminal
  over Web Serial/KISS (then BLE/audio) driving `ConnectedLink`; channels, a monitor pane, status line,
  function keys, command line. Modern shell first. *Milestone demo: connect to a real BBS/node.*
- **P2 — FBB-style BBS uplift**: connected-mode BBS *server* (ingest) + the classic command interface
  over the existing message base; add the **thread tree** (`reply_to`/`thread_id`, `SR` reply, threaded
  views); P/B/T typing, MID/BID, expert mode.
- **P3 — Forwarding + hierarchical routing tree**: parse `category @ bbs.#region.state.country.cont.WW`;
  `bbs_forward_rules` longest-prefix routing; the FBB forward protocol (proposal/accept, LZHUF) for
  `rf-fbb` partners; **fold today's bulletin federation in as the `ip-fed` partner**; White Pages for
  P-mail steering.
- **P4 — NET/ROM node + connected-mode digipeater + sysop admin**: `NetRom` L3/L4 (NODES table,
  circuits, routing); the node user CLI (Nodes/Routes/Connect/Users/MHeard/CQ/Bye); connected-mode +
  alias digipeating (extends `packages/aprs/digipeat.ts`); the sysop **admin/config** surface.
- **(Optional P0.b here)** modulo-128/SREJ in `packages/ax25` if a real partner needs throughput.
- **DoD per phase:** pure cores unit-tested; RF behaviour validate-at-deploy (hardware-path posture);
  operator-local (ingest-locality); RX stays Tier C (verify.ts untouched).

### Stage 2 — Cogmind full-app theme (`docs/24`)

### Stage 3 — Retro-shell transformation (`docs/25` P5) — the modern↔late-90s "flip"

## 5. Definition of "feature-complete for v1.0.0"

Every doc's **in-scope** deferred item is built (§2 top table): the map story closed (Stage 0); the
packet world live and theme-transformable (Stages 1+3); the app fully themeable (Stage 2); a real
landing + marketing splash (Stage 4b); and the repo released-grade (Stage 4a/c/d). The §2 "deferred/
reserved" list is **knowingly excluded** — those are reserved seams or owner-deferred (CI), not gaps.
At `v1.0.0` the trust model is **Tier B (app-geo) + honest Tier C**, with Tier A designed-for and
RF-deferred (`docs/22`) — a conscious, documented choice, not an omission.

## 6. Risks & sequencing notes

- **Packet (Stage 1) is the long pole** and the highest-risk RF code. P0's pure, tested core de-risks
  it; keep every new layer (P2–P4) pure-core + scripted tests, with hardware as validate-at-deploy.
- **Theme before retro-shell, both after packet.** Re-skinning a moving target is waste; freeze the
  component set (Stage 1) before Stage 2/3.
- **Release prep strictly last.** Screenshots/marketing must show the final themed product, incl. the
  flip — so Stage 4b can't precede Stages 2–3.
- **Don't gate the tag on reserved items.** §2's deferred list (esp. CI, AXIP/44net, Backend B) is
  post-1.0 by design; shipping 1.0 without them is correct, not incomplete.
